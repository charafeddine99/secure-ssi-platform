# 03 – Bugs and Findings

Severity scale: Critical, High, Medium, Low, Info. "Fixed" means changed in this audit and re-tested (see `04_FIXES_IMPLEMENTED.md`).

| ID | Severity | Module | Finding | Status |
|---|---|---|---|---|
| F-01 | **High** (QR feature) | OpenID4VP / QR (`services/identity-service/app/api/v1/oid4vp.py`) | Without `IDENTITY_PUBLIC_ORIGIN` (the default), `request_uri` in the QR and in the same-device `openid4vp://` link was built from `request.base_url`. Behind the gateway that is `http://identity-service:8000`, an internal Docker hostname no phone or browser can reach. It also leaks the internal service name. Same family as the earlier "Not Found Data User" QR problem. | Fixed |
| F-02 | **Medium** | Recovery step-up (`docker-compose.yml`) | Identity signs step-up tokens with `IDENTITY_STEP_UP_SECRET`; recovery verifies them with `RECOVERY_STEP_UP_SECRET`. Compose wired them as two independent variables. With recovery step-up on and two different values, every guardian invitation and recovery-policy change fails with 403. Reproduced on the audit stack (5 guardian checks 403). | Fixed |
| F-03 | Low | Deployment config (`docker-compose.yml`, `.env.example`) | The default `IDENTITY_MONGO_URI` / `RECOVERY_MONGO_URI` hard-code the default passwords. Changing `MONGO_APP_PASSWORD` or `MONGO_RECOVERY_PASSWORD` alone makes the identity service fail to start (`AuthenticationFailed`). Reproduced. | Fixed |
| F-04 | Info | Security defaults | In development mode, step-up, dual control and recovery step-up are off by default. `.env.example` documents that any other environment name forces them on. Not changed: the documented design. E2E was run with them on. | Documented |
| F-05 | Info | Revocation ledger | The dedicated revocation ledger (separate database and principal) is off unless `MONGO_LEDGER_*` and `IDENTITY_REVOCATION_LEDGER_URI` are set. With it on, rollback protection works: emptying the ledger without its anchor makes status lists fail closed with `LEDGER_ROLLED_BACK` (observed during resets). | Documented |
| F-06 | Info | Test harness | Two E2E checks still expect the pre-WP-32 QR design (`client_id` = public origin URL, plain authorization request in the same-device link). WP-32 deliberately moved to a signed request object with a `did:jwk` client_id and `request_uri`, verified by `wp32_scan_request_uri` (11/11), `wp32_cross_device` (13/13) and `wp32_oid4vp_security` (16/16). The two checks are outdated, not product failures. They were not edited. | Open (test drift) |
| F-07 | Info | Test harness | Under the gateway's per-IP rate limit the harness re-sends a request after a 429 wait of up to 61 s. For step-up the TOTP code expires in that time and identity correctly returns 403. Fixed in the audit harness by clearing the isolated Redis counters on each reset. No product change. | Harness fixed |
| F-08 | Info | Local environment | Windows Smart App Control (on) blocks unsigned native modules in `.venv` (`cbor2`, intermittently scikit-learn). Identity tests ran in a container instead. Security settings not changed. | Environment |
| F-09 | Info | Blockchain anchoring | `BLOCKCHAIN_ENABLED` defaults to false and compose starts no chain node. Anchoring endpoints exist; no live chain was tested. | External dependency |
| F-10 | Info | KMS | Only the development (software) key provider runs. A generic remote KMS client exists in code but no external KMS/HSM is configured or reachable. | External dependency |
| F-11 | Info | Fraud / risk | Rule-based scoring and security intelligence (rules, median/MAD anomalies, incidents). No trained ML model is shipped or loaded; `/api/v1/fraud/intel/model` reports the not-trained state. | Documented |
| F-12 | Low | DR drill tool (`services/identity-service/app/tools/platform_restore_drill.py`) | The "source database was not changed by the restore" check compares only document counts per collection of the **live** source before and after the restore. The restore writes only to separate `restore_drill_*` databases, but the platform's own background jobs (audit outbox, security-event forwarder, reconciliation) can add documents in the same seconds. Seen in both regression drills (status `RESTORED_AND_VERIFIED`, all 37 collections matched, but the count check failed and the tool exited non-zero). Root cause measured: while the stack is idle, `audit_events` and `audit_outbox` grow by 2 every ~15 s because of F-14. The initial drill (32/32) happened to run before the keys became due for re-sync. A false alarm that errs on the safe side; no data was affected. Not changed: needs a design decision (exclude `audit_events`/`audit_outbox` from the count, pause background jobs during a drill, or fix F-14). **2026-11-23:** fixed together with F-14 (FIX-4, FIX-5): the two append-only audit collections may grow but never shrink; every other count must stay exactly the same. | Fixed (unit-tested; live drill re-run pending) |
| F-14 | **Medium** (operations) | Managed-key reconciliation (`managed_key_service.py`, `managed_key_repository.py`) | Every ACTIVE key whose last provider sync is older than `IDENTITY_KMS_STALE_OPERATION_SECONDS` (60) is re-synced, and every routine sync writes two audit events (`KEY_RECONCILIATION_CLAIMED`, `KEY_RECONCILIATION_COMPLETED`) even when nothing changed. Measured on the audit stack: 190 of 360 audit events (53%) in ~1.5 h were these, about 2,880 events per key per day while idle. With many wallets this floods the audit log and the outbox, and it causes F-12. Not changed: whether routine syncs must be audited is a compliance/design decision. Recommendation: audit only state changes and failures (keep a counter/metric for routine syncs), or lengthen the sync interval. **2026-11-23, owner's decision:** audit only state changes and failures; routine syncs that change nothing are counted in the metrics (FIX-4). | Fixed (unit-tested; live re-check pending) |
| F-15 | **Medium** (availability) | Managed-key reconciliation (`managed_key_service.py`) | Found while fixing F-14. Every claim adds 1 to `reconciliationAttempts`, and a successful routine sync never reset it. After about five routine syncs (about five minutes for an ACTIVE key) the counter passed the retry limit. The next single transient provider error (for example a KMS timeout) then moved the key straight to `FAILED` (`RETRY_LIMIT_REACHED`) instead of retrying. Reproduced with a unit test on the old code: after 5 routine syncs and one timeout, state FAILED with attempts 6. | Fixed (FIX-6, unit-tested) |
| F-13 | Info | Test environment | `SECURITY_EVENT_ORIGIN` / `INTEL_ANALYTICS_ORIGIN` default to `OPERATIONAL`. A test stack must set them to `SYNTHETIC_TEST`, otherwise test events are shown as operational data (the "Synthetic test data" banner is correctly absent). Seen in the initial UI stage; corrected in the audit stack's configuration. | Documented |

No Critical findings. No broken access control, IDOR, injection or signature-verification bypass was found by the security suites (see `07_SECURITY_AUDIT.md`).
